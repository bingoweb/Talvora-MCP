## 3. Deep codebase cleanup completed in this session

The previous codebase had repeated infrastructure, several very large source files, duplicated Windows session/process code, repeated HTTP/process/file persistence helpers, stale test assumptions, and CI behavior tied to old tool counts/file layouts.

The cleanup was implemented deeply rather than only cosmetically.

### 3.1 New shared infrastructure project

Canonical shared project:

`src\Talvora.Shared\Talvora.Shared.csproj`

Important shared components:

- `AtomicFile.cs`
  - Atomic text replacement.
  - Optional backup creation.
  - Used by config/state persistence instead of repeated temp-file/move code.

- `CommandResolver.cs`
  - Shared PATH/PATHEXT executable resolution.
  - Replaces local command-resolution copies.

- `FileLog.cs`
  - Shared file logging with bounded/rotated behavior.
  - Installer and Tray logging now use this shared path.

- `JsonFileStore.cs`
  - Shared async JSON read/write.
  - Uses atomic persistence.

- `ProcessRunner.cs`
  - Shared short-lived process execution.
  - Handles argument vectors, environment overrides, timeout, cancellation, stdout/stderr, exit code, and process-tree termination.

- `TalvoraConstants.cs`
  - Shared product/endpoint/name constants.

- `TalvoraHttp.cs`
  - Shared `HttpClient` factory.
  - Centralizes TLS/redirect behavior instead of repeating `HttpClientHandler` construction.

- `TalvoraToolManifest.cs`
  - Canonical tool manifest.
  - Current count: **159**.
  - CI/runtime/source regression derive the expected count from this manifest rather than hard-coded 162/32 values.

- `TextLines.cs`
  - Shared line splitting and trailing-newline helpers.

- `WindowsSessionLauncher*.cs`
  - Shared Windows interactive-session implementation.
  - WTS enumeration, user token acquisition, environment block creation, executable/command-line creation, and `CreateProcessAsUserW`.
  - Both installer and MCP session tools now use one implementation.

### 3.2 Windows session implementation consolidated

Previously `SessionTools.cs` contained a very large independent implementation of:

- WTS enumeration,
- user token handling,
- environment parsing,
- executable resolution,
- command-line escaping,
- `CreateProcessAsUserW`,
- Win32 P/Invoke declarations.

This was consolidated into `Talvora.Shared\WindowsSessionLauncher*.cs`.

`SessionTools.cs` is now a thin MCP adapter exposing:

- `talvora_session_list`
- `talvora_session_get`
- `talvora_user_process_start`

This removes the duplicated user-session process-launch stack.

### 3.3 Installer architecture corrected

The native installer remains the canonical installation engine.

`scripts\Install.ps1` is now only a thin bootstrap:

1. Elevate if necessary.
2. When a build is required:
   - ensure Chocolatey,
   - ensure Git,
   - ensure .NET SDK,
   - run `Build-Windows-Installer.ps1`.
3. Run the canonical `Talvora-Setup.exe --silent`.

It no longer implements a second service-install/state/config engine.

New switch:

`-SkipBuild`

This is used by CI when the installer artifact has already been built.

`scripts\Reset-And-Install.ps1` now delegates to this canonical installation path instead of duplicating package/bootstrap/install behavior.

### 3.4 Installer user-context correctness

The installer can now distinguish:

- normal elevated interactive-user execution,
- LocalSystem execution.

When running as LocalSystem it resolves the active interactive user with `WindowsSessionLauncher` and uses that user's:

- SID,
- profile path,
- LocalAppData,
- registry hive,
- session.

This fixes the class of issues where an installer launched from LocalSystem would accidentally write user-scoped state/config/startup data into the system profile.

User-scoped installer operations now target the resolved installation user:

- Tray startup registration,
- previous Tray startup lookup,
- legacy user registry cleanup,
- `.codex\config.toml`,
- `%LOCALAPPDATA%\Talvora\current.json`,
- interactive Tray launch.

### 3.7 Process / HTTP / persistence duplication removed

The following families were redirected to common infrastructure:

- short-lived external commands -> `ProcessRunner`
- command discovery -> `CommandResolver`
- HTTP client creation -> `TalvoraHttp`
- metadata JSON persistence -> `JsonFileStore + AtomicFile`
- text config/state writes -> `AtomicFile`
- newline normalization -> `TextLines`

Notable exceptions are intentional:

- `JobTools` manages long-lived interactive/stdin/stdout processes, so it keeps its own process lifecycle rather than forcing it into the short-lived runner.
- network/dev-server probes still convert connection failures into structured probe results where that is the intended tool contract.

### 3.8 Service wait logic corrected

`ServiceTools` previously used blocking `Thread.Sleep(100)` loops.

It now uses async wait methods with:

- `Task.Delay`
- `CancellationToken`

Production source currently has no remaining:

- `Thread.Sleep(...)`
- `.Result`
- `.Wait()`
- `async void`
- empty `catch { }`

The remaining catches are either filtered to expected exceptions or intentionally convert operational failures to structured tool results.
